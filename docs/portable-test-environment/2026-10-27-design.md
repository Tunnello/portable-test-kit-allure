# 便携式 Python 自动化测试环境方案

## 目标

分阶段构建可复制的 Windows x64 自动化测试目录。第一阶段只解决一个端到端示例：新设备不预装 Python 或 uv，复制目录后运行包内 Python/pytest，执行 `tests\test_public_examples.py` 中的网络连通性和本地目录检查。

第一阶段不加入 Allure 报告链路；Allure CLI、JRE 和报告生成能力在第二阶段加入。等后续测试实际需要保存 Allure 结果并生成报告时，再将它们作为单独阶段加入依赖锁定、打包和离线验收。

## 第一阶段范围

### 包内内容

- Windows x64 可复制的 Python 运行时。
- pytest 及其固定版本的传递依赖。
- 示例测试 `tests\test_public_examples.py` 和共享 pytest 配置。
- 使用说明、构建/版本清单，以及运行日志目录。

示例使用 pytest 组织，并调用 `pathlib`、`shutil`、`subprocess` 等 Python 标准库，不依赖业务脚本或外部系统。Allure 报告生成能力在第二阶段加入。

### 外部前置条件

- 操作系统为 Windows x64，并可从 PATH 调用 `ping.exe`。
- 当前用户需能读取 `C:\` 根目录；示例不要求管理员权限。
- 网络连通性用例需要出站 ICMP 访问 `www.baidu.com` 和 `www.google.com`。Google 在被网络策略拦截时会失败，属于环境结果而非代码错误。
- 本地目录用例只读取 `C:\` 根目录，不修改文件或系统配置。

Python 运行环境便携化不代表网络和 `C:\` 也被打包。README 必须明确指出这些外部条件。

## 仓库现状

- 已提供一条 pytest 示例链路：
  - `tools/portable-test-env/tests/test_public_examples.py` 覆盖 ping 百度、ping Google（3 秒超时）和列出 `C:\` 根目录。
  - 示例使用 `subprocess` 调用 `ping.exe`，使用 `pathlib` 读取本地目录，不依赖业务脚本或外部系统。
- 当前仓库没有其他 Python 业务测试、Python 依赖清单或 pytest 项目配置。第一阶段的真实验收目标就是该示例；后续用例加入时重新核实依赖和前置条件。
- 示例的实际结果取决于当前网络和文件系统环境：网络用例可能因出站 ICMP 被拦截而失败。

## 方案选择

### 推荐：便携 Python 发行版 + 固定的 pytest 依赖

在 Windows x64 构建机准备适用于所选 Python 版本的便携式发行版，构建时将 pytest 和锁定依赖装入包。交付目录不依赖目标机的 Python、uv 或全局 Python 包。所用发行版必须支持复制后从相对目录启动，并在实现阶段通过空格路径、断网和干净设备验收。

采用该路线是为了优先跑通最小端到端示例，同时保留以后增加测试依赖的普通 Python 包管理能力。第一阶段固定使用 WinPython 2026-04 Windows x64 发行版中的 Python 3.13.18；构建时只复制归档内的 `python` 运行时子目录，不打包 notebook、IDE 等外层工具。官方归档为 `WinPython64-3.13.18.0dot.zip`，SHA-256 为 `50c4f17809457e411c2db30959c8fb25a958ff3a6f624080044992809509bc37`，该值已在构建前核验。

### 暂不纳入的选项

- Python embeddable package 加手动 vendoring：需自行处理 `._pth`、`site-packages` 和依赖布局，第一阶段不为此增加维护成本。
- 容器：会要求目标机先准备容器运行时，不符合复制目录即可运行的目标。
- Allure CLI/JRE：第一阶段不验收报告生成；报告能力在第二阶段加入。

## 第一阶段目录草图

```text
portable-test-kit\
  python\                 # 便携式 Python 和 pytest 依赖
  tests\
    conftest.py
    test_public_examples.py
  logs\                   # pytest 诊断日志
  README.md               # 构建、运行和外部前置条件
  bundle-manifest.json    # OS/架构、Python/pytest 版本、来源和校验值
  run-tests.cmd           # 可选薄启动器，只转发参数并调用包内 pytest
```

包内路径相对入口目录解析。示例不依赖构建机上的外部业务目录，也不写死本机路径。日志只写到包内目录。

## 运行流程

1. 用户在普通 PowerShell 或命令提示符中运行包内 `python.exe -m pytest`，或调用只负责转发的 `run-tests.cmd`。
2. `tests/test_public_examples.py` 定义网络连通性和本地目录用例，不读取业务脚本或外部配置。
3. 网络用例调用 `ping.exe`：百度用例发送 4 个请求；Google 用例发送 1 个请求，单次回复超时和进程超时均为 3 秒。
4. 本地目录用例通过 `pathlib` 列出 `C:\` 根目录，并断言目录非空且包含 `Windows`。
5. pytest 返回测试状态；任何测试日志写入包内可写目录。流程不修改系统级 `PATH`、注册表或持久化环境变量。

## 第一阶段验收标准

1. 在 Windows x64 干净设备/虚拟机中未安装 Python 和 uv，仅复制交付目录后可启动包内 Python 和 pytest。
2. 运行示例不触发 pip、uv 或其他依赖下载；网络连通性用例外。
3. 在普通用户会话中可运行示例；`ping.exe` 可用且 `C:\` 根目录可读。
4. 百度用例通过时退出码为 0；Google 用例在 3 秒内返回并给出明确的成功或超时诊断；C 盘用例能列出非空目录。
5. 缺少 `ping.exe`、`C:\` 不可读或网络请求被拦截时，测试明确失败并说明前置条件。
6. 示例执行前后系统级 `PATH`、注册表及持久化环境变量不变；示例不修改文件、不写入磁盘。
7. 交付清单记录 Windows x64、Python、pytest 及包构建版本和来源；不含运行时密钥。

Allure/JRE 不属于第一阶段验收。后续阶段若引入报告，需新增其锁定版本、来源与许可、报告生成流程、测试失败时的退出码保留行为以及离线验收。

## 风险与限制

- 网络用例的结果依赖当前网络环境；Google ICMP 可能被防火墙或网络策略拦截，测试会保留失败诊断。
- 网络连通性和 `C:\` 是外部前置条件；Python 便携包不提供它们。跨 Windows 版本或 CPU 架构的兼容性不作承诺。
- 后续用例可能新增浏览器、驱动、原生 Python 包、网络服务、凭据、外部系统或权限需求；新增前先明确外部前置条件和再分发许可。
- 便携包需放在当前用户可写位置。运行器隔离系统配置不代表任意测试代码都没有外部副作用。
- Python 发行版及 pytest 依赖的再分发许可应在构建阶段核对并随包保留声明。

## 第二阶段：Allure 本机报告

第二阶段在不改变第一阶段测试边界的前提下，为 pytest 运行增加可离线生成和查看的 Allure 报告。目标设备仍需 Windows x64、可执行的 `ping.exe` 和可读的 `C:\` 根目录；网络连通性用例需要相应的出站 ICMP 访问。不要求目标设备预装 Python、uv、Java/JRE 或 Allure CLI；Allure 报告生成本身不需要网络连接。

### 包内新增组件

- 在 Python 依赖锁中加入固定版本的 `allure-pytest`，并锁定其完整依赖及哈希。
- 单独打包 Windows x64 Allure Commandline 和便携 JRE；构建前验证归档 SHA-256，清单记录固定版本、HTTPS 来源、归档名、解压路径和包内可执行文件路径。
- 初始候选版本固定为 `allure-pytest` 2.16.2、Allure Commandline 2.46.1 和 Eclipse Temurin JRE 21.0.12.1+1。正式写入清单前，构建验收必须再次确认它们相互兼容、发布归档可用且许可证/第三方声明随包提供。
- `allure-pytest` 使用 Apache-2.0 许可证；Allure Commandline 和 Temurin JRE 的再分发声明须随交付包保留。

### 报告运行流程

1. `run-tests.cmd` 继续从包内相对路径启动包内 Python，再调用报告运行器；不回退到系统 Python。
2. 报告运行器从包内清单读取路径，只清理包根目录下由本工具管理的 `allure-results` 和 `allure-report`。
3. 报告运行器调用包内 pytest，并将 `allure-results` 作为受管理的 `--alluredir`。用户不得覆盖该参数，以防结果写到未受管理的位置。
4. pytest 结束后，只要存在 Allure 结果文件，就使用包内 Allure CLI 生成 `allure-report`；pytest 测试失败不能阻止生成失败测试报告。
5. 报告生成成功后，使用 `allure open --host 127.0.0.1` 打开报告。Allure 自动启动本机 HTTP 服务并打开默认浏览器；使用 CLI 默认随机端口，服务持续到用户在启动器终端按 Ctrl+C。监听地址不得使用 `0.0.0.0` 或其他非回环地址。
6. 启动器在报告服务关闭后返回原始 pytest 退出码。若 pytest 成功但报告生成或启动失败，返回非零；若 pytest 已失败且报告也失败，明确显示两类错误并保留 pytest 的失败退出码。没有结果文件时不得打开旧报告；pytest 已非零退出时保留该状态，否则以非零退出。

Java 相关环境变量只为 Allure CLI 子进程设置，指向包内 JRE；不得持久修改系统 `PATH`、`JAVA_HOME`、注册表或其他环境变量。运行时禁止网络访问；构建机下载的所有制品须先校验来源和 SHA-256。

### 第二阶段验收标准

1. 离线交付包包含固定版本的 `allure-pytest`、Allure Commandline 和 Windows x64 便携 JRE，清单记录可追溯来源、SHA-256、版本及包内路径，许可证声明随包提供。
2. 在没有系统 Python、uv、Java 或 Allure CLI 的 Windows x64 目标设备断网运行时，包内工具可运行 pytest、生成 Allure 报告并自动打开 `127.0.0.1` 报告网站。
3. 报告网页中包含当前运行的测试结果；测试失败时也会生成并展示失败报告。新运行不混入先前的 Allure 结果或报告。
4. 用户关闭服务后，启动器准确保留 pytest 退出码；报告生成或服务启动错误清晰可诊断，且不能返回成功状态。
5. 报告服务仅绑定回环地址；运行不持久修改系统级环境变量、注册表或 `PATH`，且不下载运行时依赖。
6. 保留第一阶段所有边界：公开示例只进行网络探测和目录读取，不需要管理员权限，不修改系统配置，不写入磁盘。
